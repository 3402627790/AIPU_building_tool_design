## 讲解：ops API 是什么

用户问「什么是 ops api」，定位到本仓库的 `python/src/AIPUBuilder/ops/`（文档入口 `doc/ops.rst`，automodule 指向 `AIPUBuilder.ops`）。

结论要点（后续回答同类问题可直接复用）：
- ops API = AIPUBuilder 的 Python **建图 DSL**，230+ 算子，按域分 14 个模块（math/nn/array/reduction/activation/normalization/rnn/image/detection/control/special/logical/input/common）。
- 关键认知：**不做数值计算，只往 Graph 里加 Node**。返回 `Tensor` 句柄，含 shape/dtype/quantization，`out.op` 指向新 Node；数值要等 C++ Builder 编译 + 上板/仿真才有。
- 三层结构：Python 包装层（装饰器 + 类型归一化）→ pybind `_C._ops` → C++ `src/core/ops/*.cpp`（infer_shape、属性校验、真正建节点）。pybind 绑定源码不在本仓库（只有 modules/btrt 下有 PYBIND11_MODULE）。
- 标准装饰器链：`@eager_mode` → `@wrap_numpy_to_tensor` → `@check_rterrors`（含 infer_shape）→ `@check_input_op`（游离 Tensor 自动补 input/constant 节点）→ 函数体 `convert_*` 归一化 → `_ops.xxx()`。
- eager mode：`enable_eager_mode("opt"/"sim"/"npu"/"exe")`，本质给节点打 `_opt/_elf/_device/_exe` 属性后 `run_node(op)` 立即执行，用于调试。
- 真实用法范例见 `scripts/cost_model/create_dataset.py`（ops.input → ops.conv2d → 改 op.name / tensor.name → 喂给 profiler）。

## aipugc-llir（LLIR 工具链，用户 10.12 重写后）

定位：LLIR = Low-Level IR = LLVM IR（.ll/.bc），特指周易/Compass 设备 kernel 的底层 IR（triple `zhouyi-unknown-compass`、调用约定 `zhouyi_kernel`、`ptr addrspace(1)`、`llvm.zhouyi.thread.id.x` 等 intrinsic）。

10.12 改版后由「只能加载」升级为「加载 + 标注 + 编译」三合一：
- `src/mlir/include/aipugc/LLIRTool.h` + `mlir/aipugc/LLIRTool.cpp`（替代旧 LLIRLoader）：`loadLLIRFile(ctx, file, priorities, defaultPriority)`、`compileLLIRToObject(in, out, opts)`、`printLLIRLoadSummary`。
- kernel 优先级：`--priority func=N`（可重复）/ `--default-priority`；只对 `CallingConv::Zhouyi_Kernel` 生效，写成 LLVM fn attr `cpsPriority`，导入 MLIR 后转成 `cps.priority` i32 属性。
- 编译到 .o 不再 dlopen 外部库，改为**直接调 LLVM Zhouyi 后端**：`compileLLIRToAssembly`（TargetRegistry + TargetMachine + legacy PassManager + addPassesToEmitFile(AssemblyFile)）→ `assembleToObject`（MC 层：MCAsmParser + MCObjectStreamer）。需在可执行文件侧链接 LLVMZhouyiCodeGen/Desc/Info/AsmParser + LLVMCodeGen/Target/MC/MCParser。
- 新增 `src/mlir/llir_tool_capi/` → `libAIPULLIRToolC.so`，导出 C ABI `aipu_llir_compile` / `aipu_llir_version`，供 `src/builder/llir_compiler.cpp` dlopen（即两阶段编译 `DefferredCompiler` 那条路）。头文件 `src/mlir/include/LLIRToolCApi.h`。
- `mlir/aipugc/KernelABIPass.cpp`：zhouyi 路径把「返回 memref」的函数签名改成 cps 设备 ABI（结果变出参），`main.cpp` 在 `--llvm-target zhouyi` 且降到 affine 时挂上。
- libAIPUMLIR 用 `FILE(GLOB_RECURSE mlir/**.cpp)` 收集，新 .cpp 自动入编。

我做的修复：`tool/aipugc/llir_load_main.cpp` → `llir_main.cpp`（git mv，配合新目标名 `aipugc-llir`）；`tool/aipugc/CMakeLists.txt` 内容被重复粘贴两遍 → 去重，并给 `aipugc-llir` 补 `target_link_libraries`（原先完全没有，会导致 LLVMInitializeZhouyi* undefined）。

## 讲解：两段式编译（two_stage_compilation）

代码事实（全仓库仅两处引用）：
- 开关注册：`src/builder/tools.cpp:410` 把 `Constants::two_stage_compilation` 放进 global_switches，从命令行/配置读 bool 写进 `BuilderConfig`。
- 唯一使用点：`src/builder/mqbuilder.cpp:374` `phase_device_code_gen()`；打开后把 device_lib_names 的值换成 `.bc`（目前硬编码只支持 `isnan_naive_float32_int32` → `isnan_x3u_kernel_obj.bc`，其它 ERROR "unsupport"），交给 `DefferredCompiler::compile_to_obj()` 编成 .o，再 `code_gen.set_device_lib()` → `CodeGenerator::gen_device_code()` → `LinkerCps` 链接进 Compass ELF。
- 一段式（默认）：kernel `.cps` 由 cpscc 离线编成 `.o` 打进 `.a`；`KernelAdapter::get_device_lib()` 只做 kernel 名 → lib 名映射，`code_generator.cpp:59-104` 先找文件再找 .a，直接链接。
- 差异本质：交付物从「目标码 .o」变成「LLVM IR .bc/.ll（zhouyi-unknown-compass）」，第二阶段推迟到 GBuilder 构建期，因此可以按最终 target/optLevel/functionSections/kernel 优先级再生成代码。
- 配套：`DefferredCompiler` 名字即"延迟编译器"；`src/mlir/llir_tool_capi` 导出的 `aipu_llir_compile` 就是第二阶段的实施者。

注意（本工作区快照）：`include/core/constants.h` 里**没有** `two_stage_compilation` 常量的定义，而 tools.cpp 引用了它 → 这份快照直接编译会报未声明，服务器上可能已补。
